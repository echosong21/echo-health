## 二、⚠️ 读这张表前必须知道：索引是近似检索

`law_docs` 与 `echo_health_v2` 都使用 Milvus **`AUTOINDEX`**（托管近似索引）。

实测（同一查询连续两次）：

```
第 1 次: 0.7824 / 0.685  / 0.6785
第 2 次: 0.7824 / 0.6878 / 0.6781
```

- **top-1 稳定**，第 2 名之后有 ±0.003 的天然波动
- 这不是缺陷，是近似检索的固有特性

**⇒ 基线对比应看「命中率 / top-1 / MRR / 前 N 名 source 序列」，
不要用具体分值做等值比较。** 用分数比较会得到"每次跑都不一样"的错误结论。

若确实需要分值级复现，只能改用 FLAT（精确）索引，代价是检索变慢。

## 三、已知缺口：健康领域尚无金标集

`evals/golden_questions.json` 目前是 **`law` 领域**的题集。

拿它去跑 `echo_health_v2`（健康语料）会得到：

```
★期待来源居首 0/17 = 0.0%    MRR = 0.25
判定分布 {'miss': 16, 'partial': 1}
```

这个结果**没有意义** —— 法律问题查健康库必然全 miss。它是领域不匹配，不是检索质量问题。

**⇒ 要给健康领域做基线，必须先建一套健康金标集**（题目 + 期望来源 + 锚点）。
在此之前，健康领域的质量只能靠端到端抽样验证（见 README 第八节的真实样例）。

## Performance & Cost

### 5.1 N+1 修复前后对比

多形态召回原本是**串行**的：4 个形态各发一次 `client.search`，延迟逐个相加 ——
这是典型的 N+1 式浪费（一个请求打 N 次库，还得排队）。

| 阶段 | commit | 实现 | 平均延迟 | 测量口径 |
|---|---|---|---|:--:|
| **before**（串行） | `e0c1a0a` | 4 形态串行 `client.search` | **392 ms** | 热态，17 题平均 |
| **after**（并发） | `36e6a35` | `ThreadPoolExecutor` 并发 | **234.6 ms** | 同上 |
| **继承后**（本仓） | `c612845` | 同 after（建仓即并发） | **214.4 ms** | 同上 |

**口径内提升：392 → 234.6 ms（−40%）。**

> ⚠️ **一个必须说明的边界**：另有一份「4 次串行 Milvus 检索实测 **16.7s**」的记录，
> 但它**测量条件不明**（极可能含冷启动、BM25 索引加载、首次 embedding 等一次性开销），
> 与上表的「热态 17 题平均」**不是同一口径** —— 相差 42 倍也印证了这一点。
> **⇒ 只有 392 → 234.6 ms 这一组可互相比较；16.7s 不参与该对比。**

> ⚠️ **本仓并非 N+1 的修复现场**：`echo-health` 的 `src/retrieval.py` 自首个提交
> `67d4aee` 起就是并发实现（`git log -S "ThreadPoolExecutor"` 只命中该初始提交）。
> 修复动作发生在 `rag-service`（`36e6a35`），本仓继承的是修复后的代码。

且命中率 17/17、top-1 70.6%、MRR 0.8284 **三项逐位一致**。

**⇒ 依赖注入重构未改变检索行为。** 该结论是「重构只动控制流、不动检索逻辑」的直接证据。

## 四、复现命令

```bash
# law 领域基线（本文件记录的就是这一项）
DOMAIN=law python evals/run_eval.py --mode multi --per-form 3

# 健康领域（需先补金标集）
DOMAIN=health python evals/run_eval.py --mode multi --per-form 3
```

结果自动落 `evals/results/results_<日期>_<集合>_<模式>_pf<N>.jsonl`。

⚠️ 评测的可靠前提是：**语料、切分参数、embedding 模型三者固定**。
换其中任何一个，历史指标都不可比 —— 因为向量空间变了。
