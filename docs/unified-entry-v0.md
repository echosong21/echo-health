# A. 依赖全部离线（17:00）

## 为什么这份证据里有两个 503

**这不是缺陷，恰好是本设计的两个不同语义**：

| 端点 | 状态码 | 含义 |
|---|---|---|
| `/health` | **503** | Milvus（**必需品**）不可用 ⇒ 服务确实不能工作 |
| `/query` | **503** | 依赖层故障 ⇒ **不是内部错误**，调用方应稍后重试 |

**如果 `/health` 在 PostgreSQL 挂掉时也返 503，那才是错的** —— 记忆层有熔断降级，
PG 挂了照常答。本次环境里两个依赖都停了，所以看不到 `degraded` 分支；
那个分支由 `tests/test_api.py::test_health_degraded_when_pg_down` 覆盖。

---

## ① `GET /health` → HTTP 503

```json
{
  "status": "unavailable",
  "dependencies": {
    "milvus": "down",
    "postgres": "down"
  },
  "detail": "检索后端不可用，服务无法回答问题"
}
```

**读法**：
- `dependencies` **分别报告**两个依赖 —— 只回一个总状态无法定位是谁挂了
- 状态码由**必需品**（Milvus）决定；`postgres: down` 不影响 503 的判定，
  它只影响 body

## ② `GET /tools` → HTTP 200，count=7

```
· common.discovery.list_domains      [read]  列出可用的知识领域，含每种的检索形态与集合名
· common.discovery.health_check      [read]  检查向量库 / embedding / 重排服务与熔断器的当前状态
· common.ops.get_index_status        [read]  查询某集合的行数、索引类型与状态
· common.ops.reindex                 [write] 重建某领域的索引；默认只预演，需显式传 dry_run=false 才真的执行
· common.safety.get_rules            [read]  返回该领域的禁止断言、免责声明、计划变动上限与急症信号
· common.safety.check_input          [read]  检查用户输入是否需转介急症，或触及禁止断言
· common.safety.check_output         [read]  检查生成的回答是否含禁止断言；命中则整条拒答（不改写）
```

**这是静态镜像**，与工具注册表的一致性由
`tests/test_api.py::test_tools_mirror_matches_registry` 保证 ——
注册表加工具而镜像没同步，测试会红。

**为什么不运行时跨仓读**：注册表在另一个仓库，生产部署时两个服务可能在不同容器，
文件系统不共享。跨仓读只发生在测试，不发生在部署。

## ③ `POST /query` → HTTP 503

请求：

```json
{"question": "高血压和糖尿病该注意什么"}
```

响应：

```json
{"detail": "依赖不可用：MilvusException"}
```

**这条最关键** —— 它验证了两个判断：

**（1）503 而不是 500**

`MilvusException` **不继承** `ConnectionError`，所以按异常类型白名单判断会漏。
实现改用**探针归因**：失败时问一句「依赖现在活着吗？」

```
依赖 down ⇒ 503（这个失败是它造成的）
依赖 up   ⇒ 500（那是我自己的 bug）
```

调用方据此决定「等会儿重试」还是「报 issue」。

**（2）一个实现细节的代价**

失败路径会多一次探针调用（毫秒级）。**这个代价是刻意接受的** ——
失败路径本来就不该追求快，而正确归因比快重要。

# B. 依赖全部在线（17:50）

**环境**：Milvus（云服务器隧道）与 PostgreSQL 均在线；集合 `law_docs`，22,900 条。

## ① `GET /health` → HTTP 200（首次调用 1307ms）

```json
{
  "status": "ok",
  "dependencies": {
    "milvus": "up",
    "postgres": "up"
  },
  "collection": "law_docs",
  "num_entities": 22900
}
```

**这是 A 段看不到的分支** —— A 段两个依赖都 down，只能验证 503；这一段证明
「全 up 时确实是 200 ok 而不是别的」。

`1307ms` 包含 Milvus 首次连接建立，不是稳态值。

## ② `GET /tools` → HTTP 200，count=7（9ms）

与 A 段一致（静态镜像，不依赖任何外部服务）。

## ③ `POST /query` 单焦点 → HTTP 200

请求：`{"question": "劳动合同解除的条件是什么"}`

```
mode       = planned
subtasks   = ['劳动合同解除的条件是什么']       <- 1 个，正确没拆
per_task_n = {'劳动合同解除的条件是什么': 2}

stage_ms = {
  'plan_ms': 5948.5,
  'retrieve_per_task_ms': {'劳动合同解除的条件是什么': 5947.4},
  'generate_ms': 1993.2
}
contexts = 2 条
answer   = 材料中未提及。
```

**⚠️ 关键读数：`retrieve` 5947ms。这是冷启动** ——
首次 `get_emb()` / `get_client()` 初始化 + Milvus 连接建立。
对比下面 ④ 的 349ms 就能看出差别，不是检索本身慢。

## ④ `POST /query` 多焦点 → HTTP 200（核心验证）

请求：`{"question": "合同违约和侵权责任的赔偿标准分别是什么"}`

```
mode       = planned
subtasks   = ['合同违约', '侵权责任的赔偿标准分别是什么']
per_task_n = {'合同违约': 2, '侵权责任的赔偿标准分别是什么': 2}

stage_ms = {
  'plan_ms': 349.3,
  'retrieve_per_task_ms': {'合同违约': 184.9, '侵权责任的赔偿标准分别是什么': 347.3},
  'generate_ms': 16306.0
}

contexts = 4 条
融合结果按子任务分布: {'合同违约': 2, '侵权责任的赔偿标准分别是什么': 2}
```

**这一段同时证明了四件事**：

| # | 证据 | 数值 | 说明 |
|:--:|---|---|---|
| 1 | **拆分生效** | 2 个子任务 | 规则命中「和」，且第二段补全了谓词 |
| 2 | **并行生效** | 184.9 + 347.3 = 532ms 总和，**wall 只有 349.3ms** | 若串行会接近 532ms |
| 3 | **融合均匀** | 两个子任务各 2 条 | RRF 没有偏向某一路 |
| 4 | **回答覆盖两问** | 见下 | 不是只答一半 |

**回答原文**：

> 合同违约的赔偿标准：材料中未提及。
>
> 侵权责任的赔偿标准：医疗侵权的赔偿范围包括医疗费、误工费、护理费、交通费、
> 住宿费、住院伙食补助费、残疾赔偿金/死亡赔偿金、被扶养人生活费、丧葬费、
> 精神损害抚慰金；著作权侵权按权利人的实际损失或侵权人的违法所得赔偿，
> 法院可酌情确定（如本案判赔 700 元）。

**⚠️ 注意第一个子问题「材料中未提及」** —— 这不是缺陷：
`law_docs` 语料里确实没有合同违约赔偿标准的专门段落。**规划层的作用是让
「没找到」和「找到了」被分别报告，而不是让一个子问题拖垮另一个。**

## 延迟观察（诚实记录）

| 调用 | retrieve | generate | 总计 |
|---|--:|--:|--:|
| ③ 单焦点（**首次**） | 5947 ms | 1993 ms | 7949 ms |
| ④ 多焦点（**第二次**） | **349 ms** | 16306 ms | 16683 ms |

**两条结论**：

1. **冷启动成本比文档里写的高得多** —— DESIGN §5 记的「冷启动 637ms」只是
   `embed_query`，实际首次调用还包含 Milvus 连接建立，合计约 **5.9 秒**。
   这条已在 DESIGN 里修正。
2. **generate 是大头，不是检索** —— ④ 的 generate 16.3 秒是因为要输出两个子问题的
   完整答案（token 量约为单焦点的 3 倍）。**优化检索的收益远小于优化生成。**

## 已知边界（不在本版范围内）

- **无鉴权/限流/多租户** —— 在反向代理或 MCP 层解决
- **`/health` 的 PG 探针只探端口**，不执行 `SELECT 1` —— 端口开着但 SQL 跑不起来会漏判。
  更严的探针需要连接密码与库名，健康检查不该引入这些依赖
- **`num_entities` 在 Milvus 不可用时为 null**，不是 0 —— 区分「查不到」和「确实是空的」
- **冷启动 5.9 秒没有优化** —— 可考虑服务启动时预热（跑一次空查询），
  让第一个真实请求不必付这个成本
